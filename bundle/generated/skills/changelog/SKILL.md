# changelog

## 目的
- 変更素材を、`CHANGELOG.md`、リリースノート、埋め込み用変更説明、コメント用差分ログへ変換する。
- コミットログ、開発日誌、PR一覧、実装メモではなく、対象読者が変更内容と影響を理解し、利用、移行、運用、調査に使える変更説明を書く。

## 使うタイミング
- `CHANGELOG.md` にエントリを追加または編集する。
- リリースノートを書く。
- 他の文書やレビューコメントに差し込む変更説明を書く。
- コミット、Issue、Pull Request、diff、既存履歴から人間向けの変更要約を作る。

## 使わないタイミング
- バージョン番号、リリース可否、公開手順、承認フローだけを決める。
- Conventional Commits、Semantic Versioning、パッケージ公開手順そのものを整理する。

## 契約
- ユーザーの明示指示を最優先する。
- 既存の changelog やリリースノートがある場合は、見出し階層、日付形式、カテゴリ順、箇条書き、リンク形式を維持する。
- 変更内容、バージョン番号、リリース日、Issue/PR番号、移行手順、互換性影響、セキュリティ影響を推測で作らない。
- バージョンまたは日付が不明な場合は、既存形式に合わせて `Unreleased` に入れるか、不明な値を省略する。
- 公開面または含める情報の粒度が大きく変わる場合は、書く前に確認する。
- 確認できない場合は、比較基準と最終状態の差から更新対象を作らない依頼に限り、既存文書の粒度とプロジェクト種別から最も保守的な公開面を仮定し、推測した前提を出力内で短く明示する。比較範囲分類成果が必要な更新では、この仮定を `comparison_scope_id` の構成要素の確定に使わず、Phase 1 の `blocked` 条件に従う。
- 文章前提は `$writing` に従う。

## フロー
### Phase 1: 素材と既存形式を確認する
次の順に確認する。

1. ユーザー指示。
2. 既存の `CHANGELOG.md`、リリースノート、埋め込み先文書、コメントの形式。
3. 対象差分、コミット、Issue、Pull Request、マイルストーン、関連議論。
4. プロジェクト種別、対象読者、公開面。

既存形式から、見出し階層、カテゴリ名、バージョン表記、日付表記、リンク表記、情報粒度を読み取る。
更新対象のバージョンまたは節、変更前の比較基準、対象範囲の最終状態を表す版または時点を特定する。対象読者は `$writing` の文章前提として確定し、比較基準と最終状態の公開面を確認する。

#### 比較範囲分類成果を作る

比較基準と最終状態の差から更新対象を作るすべての更新では、利用者が両方を指定したか、Phase 1 で特定したかを問わず、対象範囲を確認する情報源と走査単位を定める。走査単位は、commit、変更ファイル、diff、Issue、Pull Requestなど、対象範囲の最終状態を確認できるものから選ぶ。比較基準、最終状態、対象文書または節、対象読者、更新対象範囲のいずれかを確定できない場合は、`comparison_scope_id` が未発行である比較範囲分類成果を `blocked` とする。文書を変更または出力を確定せず、不足する情報、その情報を確定する責務、未発行の理由、再開条件を返す。

文書を変更または出力を確定する前に、比較範囲分類成果として作業用の網羅性台帳を作る。台帳は公開する changelog またはリリースノートの一部ではない。この Skill は、情報収集成果を受領してから、対象読者と公開面に照らした掲載判断を行い、台帳を完成させる。したがって、台帳は単なる調査結果ではなく、この Skill が所有する執筆前の成果である。

台帳には、比較基準、最終状態、対象文書または節、対象読者、更新対象範囲を結び付ける `comparison_scope_id`、台帳の `ledger_revision`、対応する出力候補の `output_candidate_revision`、情報源、走査単位の確認状態、変更候補、`記載`、`除外`、`要確認` の掲載判断、根拠、`記載` の場合の対応エントリを対応付ける。候補、掲載判断、根拠、対応エントリ、または出力候補を変更した場合は、影響した版を更新する。部分更新では、指定範囲と対象外の範囲も記録する。

情報収集担当から受け取る事実候補、根拠、走査状態、未確認事項は台帳の入力に使うが、`記載`、`除外`、`要確認` の掲載判断を代行しない。対象読者と公開面に照らした掲載判断、および台帳の状態はこの Skill が所有する。

台帳の状態は、同じ `comparison_scope_id` の更新対象範囲について一つだけ定める。更新対象範囲に未確認の走査単位または `要確認` の候補が一つでもある場合は、他の条件より優先して `blocked` とする。比較範囲全体を対象に、すべての走査単位を確認し、各候補が `記載` または根拠付きの `除外` になった場合は `complete` とする。利用者が明示的に一部の範囲またはハイライトだけを求め、その指定範囲内のすべての走査単位と候補が分類済みで、対象外の範囲が記録されている場合だけ `partial` とする。`partial` は未確認項目を含む `complete` の代替ではない。

この Skill の Phase 1 から Phase 4 は台帳を作る執筆前の工程であり、Phase 5 の文書変更または出力確定は、台帳が `complete`、または許可された `partial` になってから開始する。別の実行担当へ引き渡す場合は、`comparison_scope_id`、`ledger_revision`、`output_candidate_revision`、台帳の状態、対象範囲と対象外、走査状態、候補ごとの掲載判断と根拠、未確認事項を一つの成果として渡す。`blocked` では文書を変更せず、未確認事項と再開条件を返す。

### Phase 2: 素材の信頼度を扱う
Pull Requestタイトル、Issue本文、commit message、レビューコメントは変更意図の手がかりとして扱う。
根拠は形式ではなく、対象範囲のどの状態を表すかで扱う。変更結果は、Phase 1 で定めた最終状態を確認できる実装、merged content、diff、仕様、実際の公開面などから確認する。Pull Requestやcommitに含まれる情報も、最終状態を表す場合は根拠にできる。途中状態だけを表す説明やdiffを最終事実の根拠にしない。

名称、条件、数値、対象範囲、制約は、採用するエントリの意味に必要なものを根拠で確認する。確認できない細目は推測で補わずに省略する。省略すると破壊的変更、移行、セキュリティ、データ損失、互換性、運用リスクの判断が変わる場合は、書く前に確認する。

Pull Requestやcommitにある「改善」「高速化」「安全化」「完全対応」のような効果表現は、根拠が確認できる場合だけ changelog に反映する。
根拠が弱い場合は、観測できる変更事実に書き換える。

### Phase 3: 公開面と読者への影響を決める
文章前提は `$writing` に従う。
changelog では、変更がどの公開面に現れ、対象読者の理解、判断、行動にどう関係するかを決める。

この Phase で、台帳の各変更候補について掲載判断を行う。情報収集成果にある事実候補の確認状態は根拠に使うが、対象読者と公開面に照らした `記載` または `除外` の決定はこの Skill が行う。根拠または掲載判断を確定できない候補は `要確認` とし、台帳を `blocked` にする。

候補ごとに、その変更を観測または利用する対象読者と、記録する理由を特定する。対象文書の読者に関係しない変更や、その読者の公開面に現れない内部操作手段だけの変更は除外する。

変更対象の名称と対象範囲は、最終状態の公開面と一致させる。

- ライブラリ / SDK: API、型、コマンド、設定、互換性、移行。
- CLI / 開発ツール: コマンド、オプション、出力、設定、自動化ワークフロー。
- アプリケーション: 画面、操作、データ、通知、既定値、サポート影響。
- 内部基盤 / インフラ: 運用手順、信頼性、監視、デプロイ、障害対応。
- 低レイヤーのフレームワーク / プロトコル: 挙動、互換性、性能、連携先契約。

changelog では、観測可能な挙動、ワークフロー、API、コマンド、設定、互換性、移行、セキュリティ、運用影響を優先する。
内部変更は、デバッグ性、拡張性、性能、信頼性、契約、運用リスクが変わる場合だけ含める。

### Phase 4: 変更結果へ絞る
コミットやPull Requestを1対1で写さない。

Phase 1 で確定した比較基準と最終状態を比べ、対象読者にとって記録する価値がある変更結果だけを候補にする。
同じ成果へ至る途中状態、試行、やり直し、実装手順、採用されなかった案、後続変更で置き換えられた内容、最終状態に差を残さない変更は除外する。最終結果の理解に実装情報が必要な場合は、独立したエントリにせず必要最小限だけ結果へ統合する。
各エントリには、変更結果を特定し、その影響を理解、判断、行動するために必要な詳細だけを残す。完全な仕様、網羅的な列挙、内部実装の細目、変更されない事項は、この役割を持たない場合は除外する。

- 対象読者にとって1つの変更結果を複数コミットが実現している場合は、1エントリへ統合する。
- 1つのPull Requestに、対象読者にとって複数の変更結果がある場合は、複数エントリへ分割する。
- 公開面または対象読者の理解、判断、行動に影響しない機械的リファクタリング、テストのみの変更、整形、内部移動、足場作成、依存更新は、挙動、互換性、性能、セキュリティ、信頼性、運用性、公開契約が変わらない限り除外する。

この Phase の候補選定後に、台帳の各候補を `記載` または根拠付きの `除外` に更新し、`記載` の候補を出力エントリへ対応付ける。`要確認` が残る場合は、Phase 5 へ進まない。

素材に次が含まれる場合は、エントリまたは補足で明示する。

- 破壊的変更。
- 非推奨化。
- 削除。
- 必要な移行手順。
- 挙動または既定値の変更。
- API、コマンド、オプション、スキーマ、プロトコル、ファイル形式、出力形式の変更。
- セキュリティ影響。
- データ損失、互換性、運用上のリスク。
- 既知の制約や未対応範囲。
- 利用者に見える修正。
- プラットフォーム、ランタイム、形式、連携先の追加または削除。

破壊的変更、削除、移行手順、セキュリティ影響を曖昧な表現で隠さない。

### Phase 5: 出力先に合わせて書く
#### CHANGELOG.md
既存形式が無い場合は、Keep a Changelog を基準にする。

```md
## [Unreleased]

### Added

- Added ...

### Changed

- Changed ...

### Deprecated

- Deprecated ...

### Removed

- Removed ...

### Fixed

- Fixed ...

### Security

- Fixed ...
```

リリース済みバージョンを書く場合は次を標準形にする。

```md
## [x.y.z] - YYYY-MM-DD
```

最新バージョンまたは `Unreleased` を上に置く。
既存 changelog が空カテゴリを残していない限り、空カテゴリは書かない。

#### 埋め込み用エントリ
出力先の見出し階層に合わせた短いセクションにまとめる。
出力先が `Changelog` 見出しを用意している場合は、見出しを重複させず、項目だけを書く。
見出しも作る場合は、周囲の見出し階層に合わせる。

```md
- Added ...
- Fixed ...
```

項目数が少ない場合はカテゴリ見出しを省略し、十分な件数がある場合だけカテゴリ分けする。
カテゴリ見出しを書く場合は、`Changelog` より1段下の見出し階層にする。

#### リリースノート
リリース全体の目玉がある場合だけハイライトを置く。
詳細は変更種別またはユーザー影響ごとにまとめる。
説明的な文章にしてよいが、開発文脈ではなく成果と影響を書く。

## 変更カテゴリ
既存文書に分類がある場合はそれに従う。
無い場合は Keep a Changelog の分類を使う。

- `Added`: 新機能、コマンド、API、オプション、対応対象、利用可能になった能力。
- `Changed`: 挙動、意味論、既定値、出力、検証、ワークフロー、性能、互換性の変更。
- `Deprecated`: まだ使えるが、今後の削除や非推奨が決まったもの。
- `Removed`: 削除された機能、API、コマンド、オプション、挙動、対応対象。
- `Fixed`: 不具合修正、正確性修正、信頼性修正、回帰修正。
- `Security`: 脆弱性修正、強化、資格情報の扱い、露出低減。

既存文書が `Performance`、`Documentation`、`Migration`、`Breaking`、`Renamed` などを使う場合は、その形式に合わせる。
既存形式が無い場合、rename は `Changed`、性能改善は不具合修正でない限り `Changed`、ドキュメントのみの変更はドキュメントが利用者に見える成果物である場合だけ含める。

破壊的変更は該当カテゴリ内で明示する。

```md
### Changed

- **Breaking:** Changed the configuration file format to reject unknown fields.
```

## Security エントリ
Security impact がある場合は、ユーザーまたは既存リリース方針が示す開示粒度に従う。
未公開の脆弱性詳細、悪用手順、影響範囲を推測で書かない。
依存更新は、既知の脆弱性対応、資格情報保護、露出低減などの利用者影響が確認できる場合だけ `Security` に入れる。

## エントリの粒度
- 1つのエントリには、1つの変更結果だけを書く。箇条書き形式では、これをトップレベルの項目にする。
- 同じ変更結果に属する条件、対象範囲、移行、制約、補足が必要で、一文にすると異なる役割が混ざる場合は、出力先の形式に合わせて別文またはインデントした子項目へ分ける。
- 補足だけでも別の変更結果を表すもの、別カテゴリの変更、無関係な変更は、別のエントリへ分ける。箇条書き形式では、別のトップレベル項目にする。
- 1文または1行への圧縮を優先しない。子項目は、Phase 4 の採用条件を満たさない詳細を残すために使わない。
- 変更対象、変更内容、対象読者への影響を一読で分かる順序にする。
- 英語では `Added`、`Changed`、`Deprecated`、`Removed`、`Fixed`、`Renamed`、`Improved`、`Documented` などの変更動詞から始める。
- 「改善」「対応」「調整」のような広い語だけで終えない。何がどう変わったかを書く。
- 確認していない効果を断定しない。性能、安定性、セキュリティ、互換性の効果は根拠がある場合だけ書く。
- 後で参照する必要のない内部名、ブランチ名、コミットハッシュ、担当者名を出さない。
- 変更理解に必要な固有名、API名、コマンド名、設定名は省かない。

避ける例:

```md
- Refactor parser internals.
- Build profile parser cleanup.
- PR #123.
- Implement FooService.
- Update dependencies.
- Improved various behaviors.
```

変更結果を伝える例:

```md
- Changed build profile validation to reject unknown nested fields.
- Fixed build profile loading when the profile path contains spaces.
- Added support for resolving Unity Build Profile assets during build input selection.
```

## エントリ確認
- Phase 1 で確定した比較基準と最終状態の差として成立し、途中状態だけの項目がないか確認する。
- 出力を確定する前に、最終候補と同じ `comparison_scope_id`、`ledger_revision`、`output_candidate_revision` の網羅性台帳を更新対象範囲へ再照合する網羅性レビューを行う。各走査単位と変更候補について、確認状態、掲載判断、根拠、`記載` の場合の対応エントリを確認する。レビュー結果には、照合した三つの識別子と確認した状態を記録する。
- 網羅性レビューで未分類の候補または更新対象範囲内の未確認の走査単位を見つけた場合は、台帳を `blocked` に戻す。候補を `記載` または根拠付きの `除外` に分類し、台帳または出力候補を更新した場合は対応する版を更新する。版の更新前に行った網羅性レビューは新しい候補の完了根拠に使わず、現在の三つの識別子へ再照合する。比較範囲全体では最新の網羅性レビューが現在の `ledger_revision` と `output_candidate_revision` で `complete` を、明示的な部分更新では現在の両版で指定範囲について `partial` を確認するまで完了を報告しない。
- 各エントリが、対象読者にとって記録する価値がある一つの変更結果を表し、その特定または影響の理解、判断、行動に不要な詳細を含まないか確認する。
- 名称、条件、数値、対象範囲、制約が根拠と一致しているか確認する。
- PR、実装作業、担当者視点を主語にした説明で終えない。
- 何が変わらないかを省略すると変更範囲を重大に誤認し、利用、移行、運用、調査の判断を誤る場合だけ、その内容を必要最小限で書く。
- 制約、未対応範囲、移行条件は、確認できている範囲だけ具体的に書く。

## Issue / PR参照
既知の Issue または PR に基づく場合は、エントリ末尾に参照を置く。

同一 GitHub リポジトリ内の文書では短い参照を使う。

```md
- Fixed daemon startup diagnosis when Unity exits before endpoint registration. (#123)
```

外部向けリリースノートやリポジトリ外文書では、対象文書の形式に合わせて Markdown リンクまたはURLを使う。

```md
- Fixed daemon startup diagnosis when Unity exits before endpoint registration. ([#123](https://github.com/org/repo/pull/123))
```

複数参照は、そのエントリの根拠として有益な場合だけ付ける。
番号が不明な場合は参照を作らない。

## 既存CHANGELOGの編集
1. 既存の見出し階層、リンク形式、バージョン形式、日付形式、カテゴリ順、箇条書き、参照形式を維持する。
2. ユーザーが対象バージョンを指定しない場合は `Unreleased` に追加する。
3. 最新のリリースまたは `Unreleased` を上に置く。
4. 依頼が無い限り、過去リリースを並べ替えない。
5. 更新対象外の過去リリースは比較資料として読み、依頼が無い限り編集しない。不整合を見つけた場合は、今回の更新へ混ぜずに別の確認事項として報告する。
6. 既存の changelog 規約を黙って変更しない。
7. 完了前に実差分を確認し、変更が許可されたバージョンまたは節だけに収まっていることを確認する。

## Definition of Done
- Phase 1 で確定した比較基準から最終状態までの更新対象範囲について、対象読者にとって記録する価値がある変更結果を表している。
- 比較範囲全体を対象にした更新では、同じ `comparison_scope_id` の網羅性台帳が `complete` であり、現在の `ledger_revision` と `output_candidate_revision` を含めて、各走査単位と変更候補の扱いを根拠へ追跡できる。
- 比較範囲全体を対象にした更新では、最新の網羅性レビューが、同じ `comparison_scope_id`、現在の `ledger_revision`、現在の `output_candidate_revision` の台帳と出力候補について `complete` を確認している。
- 利用者が明示的に部分更新を求めた場合は、同じ `comparison_scope_id` と現在の両版について、指定範囲内の走査単位と候補がすべて分類された `partial` の台帳と最新の網羅性レビュー、対象範囲、対象外、未確認事項を成果物または完了報告へ残し、範囲全体を更新したとは報告しない。
- 途中状態、最終状態に差を残さない変更、対象読者に関係しない内部情報が独立したエントリとして残っていない。
- 変更事実、名称、条件、数値、対象範囲、制約、および重要な影響が根拠と一致している。
- 対象文書の形式、情報粒度、変更カテゴリに合っている。
- 破壊的変更、非推奨化、削除、移行、セキュリティ影響が必要に応じて明示されている。
- バージョン、日付、Issue/PR参照を推測で作っていない。
- 既存ファイルを更新した場合は、差分が変更を許可されたバージョンまたは節に収まっている。
