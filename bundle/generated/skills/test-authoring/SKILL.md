# test-authoring

## 目的
このスキルは、確定済みの契約に対して永続的な回帰検出を担う自動テスト成果物を作成、更新、整理する。
権限ある契約根拠を先に読み、テストの必要性を具体化前に判断し、採用した対象だけを最小のテスト集合へ実装する。

成果は、契約ごとのテスト採用結果、保持するテスト集合、各テストが検出する契約違反、局所実行結果、未検証の契約と回帰リスクである。
テストコードには `$code-authoring-rules` を適用し、重要な合否判定は `$test-oracle-assessment` で評価する。

## 責務境界
このスキルの入力は、依頼または合意済みの完了条件に含まれる自動テスト成果物の作成、更新、整理である。テスト実行や変更全体の受け入れ確認だけを目的とする作業は扱わない。

このスキルは製品契約を決定、補完、拡張しない。契約の判断主体、権限、採用状態、適用範囲、根拠位置は `$change-framing` の成果を使う。

自動テスト成果物は、テスト用のビルドまたは実行境界にだけ含まれるテスト本体、テストデータ、フィクスチャー、補助コードである。本番成果物へコンパイルまたは同梱されるコード、API、可視性、状態、依存、構成、条件分岐は含まない。

本番コードの設計と実装は、同じ確定済み契約を入力とする実装作業が所有する。テストの実行、制御、観測だけを理由に本番コードを変更しない。

## フロー

### Phase 1: 権限ある契約を先に読む
リポジトリの作業規則を確認した後、今回の変更目的、変更対象、適用範囲、成立させる契約、維持する契約、作業対象外、許可、受け入れ条件を定める正本または権限ある原根拠を、実装やテストの設計より先に読む。

フレーミング結果が入力にある場合も、その根拠位置から今回使う契約の原根拠を読む。フレーミング結果がない場合は `$change-framing` を適用する。

作業者が入力から作った要約、Issue、計画、仕様、テスト、実装、生成物は、権限ある主体が独立に採用したことを確認できない限り、元の根拠を超える契約決定権限を持たない。現在の実装、実行結果、既存テスト、スナップショットは現状観測として使い、それらから契約を作らない。

今回のテスト判断に使う契約ごとに、次を確認する。

- 契約命題と、その保証または失敗条件。
- 契約を所有または決定する主体と権限。
- 採用状態、適用範囲、版、再評価条件。
- 原根拠の参照位置。
- フレーミング結果の進行状態。

`進行可能` の範囲と、`部分進行可能` のうち未確定判断から独立する範囲だけを次へ進める。必要な契約が `要確認`、未採用、競合、または根拠位置を確認できない状態なら、その範囲を Phase 7 で記録する `要確認` とし、新しいテスト詳細を作らない。

この Phase が完了するまで、新しいテスト候補、テスト名、入力値、期待値、アサート、モック、フィクスチャー、スナップショット、ヘルパー、本番変更案を作らない。

### Phase 2: 詳細なしでテスト採用を判断する
Phase 1 で確定した契約を判断基準にしてから、実装と既存テストを現状観測として読み、既存の検出面と回帰リスクを確認する。

契約ごとに、具体的なテストの形を作らず、次だけを保持する。

| 項目 | 内容 |
| --- | --- |
| 契約参照 | Phase 1 で確認した契約命題と原根拠。 |
| 所有境界 | 保証を正常完了までに成立させる責務と成立時点。 |
| 契約違反 | このリポジトリの変更によって生じ得る、意味上の保証または失敗条件の違反。 |
| 既存検出 | 現在有効な既存テストが、その違反を独立して検出する範囲。 |
| 自動化の必要性 | 永続的な自動検出が必要な受け入れ条件または回帰リスク。 |
| 判定 | `作成 / 更新 / 既存で充足 / テスト不要 / 要確認`。 |

`作成` または `更新` は、次をすべて満たす場合だけ選ぶ。

- 確定済み契約と、その保証を所有する責務境界がある。
- このリポジトリが生じさせ得る具体的な契約違反を示せる。
- 現在有効な別のテストが、同じ違反を同等以上に検出しない。
- 永続的な自動検出を必要とする受け入れ条件または回帰リスクがある。
- 既存の本番契約とテスト側の成果物だけで、契約の成立または違反を観測できる。

検出すべき契約違反に対応する既存候補がなく、独立した検出面が必要な場合は `作成` とする。同じ契約違反と所有境界へ追跡できる既存候補はあるが、検出の不足または契約外の制約があり、契約に適合する検出面へ改める必要がある場合は `更新` とする。`更新` は既存候補をその場で編集する場合に限定せず、狭い観測への置換または他候補への統合を含む。既存候補が同じ違反を契約に適合する形で独立して検出済みなら `既存で充足` とし、具体的な保持、置換、統合、削除は Phase 4 で判断する。

外部依存が所有する振る舞いを変更せず返すだけの境界には、その振る舞いの追認テストを置かない。ローカルの変換、選択、制約、失敗変換を所有する境界では、そのローカル契約だけを対象にする。

保証を所有しない後続境界では、先行境界の保証を再検証せず、後続境界が新たに成立させる確定済み契約だけを対象にする。先行保証が必要な対象、時点、適用範囲を覆わない場合は、その差を権限ある契約として Phase 1 で確定してから判断する。

現在の実装、内部構造、呼び出し手順、値の保持、カバレッジ不足だけではテストを採用しない。現在動作を維持する必要がある場合は、権限ある主体が製品契約として採用した後に Phase 1 から判断し直す。

観測または制御のためだけに本番の可視性、入口、状態、依存、抽象化、構成、分岐を追加する必要がある候補は採用しない。テストとは独立した本番の要求、契約、責務によって設計変更が確定した場合は、その変更後の所有境界を Phase 1 から再評価する。

`既存で充足` または `テスト不要` は正常な完了結果である。`既存で充足` は、既存候補を保持して検出責務を担わせる判定として、Phase 4 以降の既存テスト集合の評価対象にする。必要性を確定できない契約は `要確認` とし、具体化せず Phase 7 で確認事項と未完了状態を残す。未確定判断から独立する別の候補は、そのまま判断を続ける。

判定後は、未確定判断から独立する `作成` または `更新` が一件でもあれば Phase 3 へ進む。それらがなく、`既存で充足` があるか、今回の成果に既存テストの保持、置換、統合、削除の判断を含む場合は Phase 4 へ進む。既存テスト集合を扱わず、実編集を必要とする候補もなければ Phase 7 へ進む。

### Phase 3: 採用したテストだけを具体化する
`作成` または `更新` とした対象について、対応する契約の原根拠をもう一度読む。その直後に [references/admitted-test-design.md](references/admitted-test-design.md) を読み、代表ケース、観測範囲、実行境界、重要な合否判定を最小限に設計する。

設計した重要な合否判定を `$test-oracle-assessment` で評価する。契約適合性が `適合`、独立性が `独立` であり、検出証拠が `実証済み` または `論証のみ` の候補だけを編集へ進める。評価に必要な契約根拠が不足した場合は、作った候補詳細を採用せず Phase 1 へ戻る。固有の検出価値、既存境界からの観測可能性、または契約違反の識別力を確定できない場合は Phase 2 へ戻る。

オラクル評価を通過した後、今回の成果に既存テストの保持、更新、置換、統合、削除の判断を含む場合は Phase 4 へ進む。それらを含まない場合は Phase 5 へ進む。

### Phase 4: 既存テスト集合の編集前計画を作る
既存テストの保持、更新、置換、統合、削除を扱う場合は、Phase 3 でオラクル評価を通過した新規または更新候補を含めて [references/existing-test-set-maintenance.md](references/existing-test-set-maintenance.md) を読み、対象集合、候補ごとの保持判定、計画最終集合を編集前に確定する。

計画によって契約ごとの採用判定が変わる場合は Phase 2 へ戻り、影響する候補を Phase 3 から評価し直す。計画に実編集する候補があれば Phase 5 へ進み、保持または `要確認` だけなら Phase 6 へ進む。

### Phase 5: 計画したテスト成果物を反映する
Phase 3 でオラクル評価を通過した候補と、Phase 4 で確定した計画にある `作成 / 更新 / 置換元 / 置換先 / 統合元 / 統合先 / 削除` を、テスト側の成果物へ反映する。計画最終集合に残す候補だけが、確定済み契約、固有の契約違反、オラクル評価を持つ状態にする。

置換または統合では、`置換先` または `統合先` へ契約と検出すべき契約違反を反映してから、`置換元` または `統合元` を削除する。`削除` とした候補は計画どおりに削除し、`保持` または `要確認` とした候補は変更しない。

新しい振る舞いまたは不具合修正では、本番の対象実装を変更する前にテストを実行し、確定済み契約に対応する意図した理由で失敗することを確認する。本番実装はテスト詳細から逆算せず、同じ確定済み契約を入力として実装作業が決定する。本番変更後に対象テストを局所実行し、現在の観測結果を合否判定が受け入れることを確認する。

変更前から有効な契約へテストを追加する場合は、失敗を作るために本番実装を変えない。契約違反を含む既知の証拠がない場合は、オラクルの論証と現在実装での局所成功を分けて残す。

実際のテストで合否判定、期待結果、観測経路、共通依存が計画から変わった場合は、編集後の成果物を `$test-oracle-assessment` で再評価する。局所実行の成功は、契約適合性、独立性、必要性の代わりにしない。

既存テストを更新する場合は、期待結果を現在実装ではなく、Phase 1 で確認した契約から決める。

- 契約が変わっていないテストが失敗した場合は、期待結果を現在出力へ合わせず、契約違反と観測結果を残す。
- 権限ある主体によって契約が変更された場合は、変更後の契約と回帰リスクに必要な範囲だけを更新する。
- 契約を確定できない場合は、現在のアサートを正当化または更新せず `要確認` とする。変更権限がなければ成果物をそのまま残すが、保持判定を確定せず、整理完了とは扱わない。

反映後、既存テスト集合を扱った場合は Phase 6 へ進み、それ以外は Phase 7 へ進む。

### Phase 6: 既存テスト集合を収束させる
既存テスト集合を扱った場合は、編集後に実際に残る候補を Phase 4 の計画最終集合と照合する。差がある場合は計画を更新し、影響候補の保持判定を編集前の基準でやり直す。

整理によって重要な合否判定、期待結果、観測経路、共通依存が変わったテストは、実際に残す成果物を `$test-oracle-assessment` で再評価する。整理後の対象テストと影響範囲のテストを実行し、計画した最終集合と実際の成果物を一致させる。

照合と必要な再評価を終えた後は Phase 7 へ進む。

### Phase 7: 作業状態を残す
契約ごとの採用判定、作成、更新、保持、置換、統合、削除したテスト、各テストが検出する契約違反、TestOracleAssessment、局所実行結果を残す。

テストを置かなかった契約には、`既存で充足`、`テスト不要`、または `要確認` の根拠を対応させる。`要確認` には、確認する内容、現在の扱い、判断によって変わる候補集合を示し、完了を報告しない。検出すべき契約違反が未検証のまま残る場合は、契約、回帰リスク、停止理由を示し、完了を報告しない。

## 完了条件
- Phase 1 で権限ある契約根拠を読み、契約命題、所有または判断主体、採用状態、適用範囲、根拠位置、進行状態を確認している。
- 新しいテスト詳細を作る前に、各契約へ Phase 2 の採用判定が対応している。
- 既存テスト集合を扱う場合は、オラクル評価済みの候補全体について、編集前の保持判定と計画最終集合を確定している。
- Phase 4 で計画した `作成 / 更新 / 置換元 / 置換先 / 統合元 / 統合先 / 削除` を Phase 5 で反映し、未反映の実編集を残していない。
- 最終状態に残す各テストが、確定済み契約、固有の契約違反、保証の所有境界、契約適合性が `適合`、独立性が `独立`、検出証拠が `実証済み` または `論証のみ` の TestOracleAssessment を持つ。
- 現在実装、外部依存の所有契約、内部構造、既存テスト、カバレッジだけを追認するテストが残っていない。
- テストのためだけに本番コード、API、可視性、状態、依存、構成、分岐を追加していない。
- 同じ契約違反を検出するテストが重複せず、計画した最終集合と実際に残る成果物が一致している。
- 必要性とオラクル評価とは別に、対象テストと影響範囲の局所実行結果、および未実行範囲が明らかになっている。
